# 0012: 등급 점검 보고서 검수 — 등급·사례·수치는 코드가, 뜻은 LLM 이

- 상태: Accepted
- 날짜: 2026-10-20
- 계획 항목: [`01-plan.md`](../01-plan.md) 순번 4 · 과제 1 [0005](0005-grounded-validator.md)를 도메인에 맞게 옮긴 것

## 문제

LLM 단독(Before)의 검수는 형식(30자 이상 + "예상 등급:" 줄)만 본다. 그래서 다음 초안이 모두 통과한다
(평가셋 `rating_judge.json` 오염 초안 7개 탐지 0/7, 2026-10-20 `before0`).

- 판정 결과와 다른 등급을 쓴 보고서
- 검색되지 않은 사례를 들거나 사례의 등급을 바꿔 쓴 보고서
- 통계에 없는 수치를 쓴 보고서
- 판정에 없는 항목을 근거로 들거나, 다른 게임을 이야기하거나, "반드시 12세를 받는다·심의 없이 출시해도 된다"고 단정한 보고서

## 검토한 선택지

### A. LLM 판정 하나로 모두 본다

구현이 가장 짧다. 대신 모든 초안에 LLM 호출 1회가 들고, 수치·제목 대조 같은 결정론적인 일을 확률적으로 하게 된다.

### B. 코드로 볼 수 있는 것은 코드가 먼저, 뜻은 LLM 이

과제 1 검수(0005)와 같은 구조다. 싼 것부터 보고 앞에서 떨어지면 뒤는 부르지 않는다.

## 결정

**B를 택한다.** `agent/rating/check.py`의 `RatingValidator`:

1. 형식 — 30자 이상 + "예상 등급: <등급>" 줄
2. 등급 일치 — 보고서의 예상 등급 = 코드가 계산한 등급(0011)
3. 사례 대조 — 「제목」(등급 …)으로 든 사례가 검색된 사례인가, 괄호 속 등급이 실제와 같은가. 제목은 띄어쓰기·문장부호·대소문자를 무시하고,
   줄여 쓴 제목(3글자 이상)이 검색된 제목에 들어 있으면 같은 사례로 본다.
4. 수치 대조 — 통계 Tool 결과·사례 수·게임 설명에 있는 수치만 허용. 등급 이름의 12·15, 청소년 기준 나이 18·19, 항목 수 7은 늘 허용한다.
   사례 제목·괄호, 따옴표 속 설명 인용, "단계 N", 목록 번호는 수치로 보지 않는다. 통계의 결정일 범위는 근거에서 뺀다 —
   날짜 숫자가 지어낸 작은 수치를 덮어 주지 않게(과제 1에서 `last_checked`를 뺀 것과 같은 이유).
5. LLM 판정(qwen3:8b) — 설명한 그 게임을 점검했는가(relevant), 판정 결과와 맞고 단정·잘못된 안내가 없는가(faithful).

불합격이면 이유를 피드백으로 재작성(최대 3회). 3회째에도 떨어지면 경고를 붙여 내보낸다(과제 1과 같다).
보고서 작성 프롬프트에 사례 인용 형식(「제목」(등급 · 내용정보))과 "날짜·기간은 쓰지 않는다"를 넣어, 코드 검사가 읽을 수 있는 모양으로 쓰게 했다.

## 한계와 트레이드오프

- 사례 인용은 「」로 감싼 것만 본다. 작성 모델이 형식을 어기고 제목을 그냥 쓰면 코드가 못 본다 — 그때는 LLM 판정에 기댄다.
- 줄여 쓴 제목을 같은 사례로 보는 규칙 때문에, 짧은 제목이 다른 제목에 우연히 들어 있으면 엉뚱한 사례와 대조할 수 있다.
- 수치 규칙이 엄격해서 작성 모델이 맞는 말을 해도(예: "2024년 이후 사례") 재작성될 수 있다. 재작성마다 작성 LLM 호출 1회가 더 든다.
- LLM 판정은 판정 결과를 사실로 믿는다. 판정 자체가 틀렸으면(과소·과대평가) 검수가 못 잡는다 — 검수는 "보고서가 판정과 맞는가"를 볼 뿐이다.
- 판정 JSON 이 깨지면 통과로 둔다(과제 1과 같다).
