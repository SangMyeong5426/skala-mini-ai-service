# 0004: 대상 시스템 추정과 되묻기 — auth-service 기본값 폴백 대체

- 상태: Accepted
- 날짜: 2026-10-20
- 계획 항목: [`01-plan.md`](../task1/01-plan.md) 순번 3 · 설계 [`03-design.md`](../task1/03-design.md#항목-3--대상-시스템-추정되묻기)

## 문제

시스템명이 질문에 없으면 세 곳(`graph._extract_system_name`, ollama·openai `plan` 프롬프트의 "언급되지
않았으면 auth-service를 기본으로 조사하라", `_guess_target(s)`)이 auth-service로 채운다. 그래서
"캐시 히트율이 떨어졌어요"도, 모니터링 대상이 아닌 "billing-service"도, "서버가 좀 이상한데?"도 모두
auth-service를 진단했다. 대상 평가 15문항에서 base 6/15(되물어야 할 5건 0/5, 엉뚱한 진단 7건).
thinking을 끈 step1에서는 0.6b가 대상을 더 넓게 잡아 5/15, 엉뚱한 진단 10건으로 나빠졌다.

## 검토한 선택지

### A. 프롬프트에서 기본값 문구만 지운다

LLM이 대상을 정하는 구조는 그대로라, 0.6b가 시스템을 지어내거나 빠뜨리는 문제(step1의 i04·i07은
다섯 시스템을 다 조사)가 남는다. 못 정했을 때 무엇을 할지도 정해지지 않는다.

### B. 코드가 대상을 정하고, 못 정하면 되묻는다

이름 매칭 → 대상 밖 이름 판별 → 시스템 설명과의 의미 유사도 순서로 정하고, 확신이 없으면 진단하지 않고
되묻는다. LLM은 "여러 시스템을 비교 분석할지"만 판단한다.

## 결정

**B를 택한다.**

| 순서 | 조건 | 결과 |
| --- | --- | --- |
| 1 | 카탈로그 시스템명이 질문에 있다 | 등장한 전부, 등장 순서대로 (`name-match`) |
| 2 | `xxx-service` 꼴인데 카탈로그에 없다 | 되묻기 — 모니터링 대상이 아니다 (`unknown-system`) |
| 3 | 질문 ↔ 시스템 설명 유사도 1위 ≥ 0.40, 2위와 차이 ≥ 0.04 | 1위 (`semantic`) |
| 4 | 그 밖 | 되묻기 — 특정할 수 없다 |

| 파일 | 변경 |
| --- | --- |
| `data/systems.json` · `mcp_server.py` | 시스템 카탈로그(설명 포함)를 MCP Resource `catalog://systems`로 제공 |
| `agent/mcp_client.py` | `find_resource` — 정적 resource도 서버를 미리 가정하지 않고 조회 후 요청 |
| `agent/target.py` | `TargetResolver` |
| `agent/graph.py` | `plan_node`가 리졸버로 대상을 정하고, 못 정하면 research 0개 + `ClarifyRequested`. 새 노드 `clarify`(LLM 없이 카탈로그 안내), 조건 엣지 `plan → clarify \| gate`. LLM plan은 대상이 둘 이상일 때만 |
| `web_chat.html` | 되묻기 단계 문구 |

min_score·margin은 평가 세트가 아니라 조정용 문장 18개(`tools/tuning/target.json` — 시스템을 맞혀야 할
12개, 되물어야 할 6개)로 정했다. 모두 맞히는 조합 중 경계 여유가 가장 큰 것을 골랐고, 지시문을 붙이지
않는 쪽이 여유가 더 컸다(0.020 대 0.006).

**base의 기본값 코드는 지우지 않았다.** `TARGET_RESOLVER=legacy`로 원본 동작을 재현할 수 있어야
Before를 같은 코드로 다시 잴 수 있다. 새 경로는 그 코드에 닿지 않는다.

## 한계와 트레이드오프

- **"서버"·"사이트" 같은 넓은 단어가 web-01로 끌린다.** 설명 문구가 판정을 좌우한다. 설명을 고치면
  다른 질문의 결과가 바뀔 수 있어, 고칠 때는 조정용 문장으로 다시 정한다.
- **임계값을 올리면 진단할 질문까지 되묻는다(과잉 되묻기).** 지금은 진단 10/10이라 여유가 있지만
  조정용 문장 18개로 정한 값이라 표본이 작다.
- **대상 하나면 LLM 계획을 건너뛴다.** 비교 분석은 여러 시스템일 때만 의미가 있어 잃는 것은 없다고 봤지만,
  MCP Prompt(진단 절차)도 대상이 둘 이상일 때만 쓰인다.
- **카탈로그를 관리해야 한다.** 시스템이 늘면 `systems.json`과 `monitoring.json`을 함께 고쳐야 한다
  (둘이 어긋나면 테스트가 실패한다). 기동 시 MCP 왕복이 하나 는다.
- 되묻기 답은 템플릿이라 대화가 한 번 더 오간다. 사용자 경험상 비용이다.
