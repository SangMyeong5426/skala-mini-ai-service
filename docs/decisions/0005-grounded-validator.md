# 0005: 검수에 수치 대조와 LLM-as-judge 근거 검증

- 상태: Accepted
- 날짜: 2026-10-20
- 계획 항목: [`01-plan.md`](../01-plan.md) 순번 4 · 설계 [`03-design.md`](../03-design.md#항목-4--검수-근거-검증)

## 문제

`validate_node`는 "30자 이상 + `1)` 포함"만 본다. 형식만 지키면 수치를 지어내도, 질문과 무관한 시스템을
진단해도, degraded를 정상이라고 결론 내려도 통과한다. 검수 평가 12건(정상 5 · 오염 7)에서 base는 오염
초안을 하나도 못 잡았다(0/7). 오염 초안 하나(b1)는 실제 웹 채팅 응답 원문이다.

## 검토한 선택지

### A. LLM 판정만 붙인다

한 번에 모든 결함을 볼 수 있지만, 모든 검수마다 LLM을 부르고, 판정 모델이 틀리면 그대로 통과한다.

### B. 코드 검사만 강화한다 (수치 대조)

싸고 결정론적이다. 지어낸 수치는 잡지만, 수치는 맞는데 판단이 틀린 경우(질문 무관, 결론 왜곡, 지표
바꿔치기)는 원리상 못 잡는다.

### C. 세 겹 — 형식 → 수치 대조 → LLM 판정

싼 것부터 보고 앞에서 떨어지면 뒤는 부르지 않는다. 지어낸 수치는 LLM 없이 잡고, LLM은 수치로 못 보는
판단 오류만 맡는다.

## 결정

**C를 택한다.**

| 단계 | 검사 | 비용 |
| --- | --- | --- |
| ① 형식 | 30자 이상 + `1)` (base 그대로) | 0 |
| ② 수치 대조 | 초안의 수치가 수집 사실(모니터링 값·알림 문구·runbook·분석)과 질문에 있는지. 번호 표시(`1)`)와 알림 개수·시스템 수는 허용, 확인 시각은 근거에서 제외 | 0, 결정론 |
| ③ LLM 판정 | quality 모델에 질문·수집 사실·초안을 주고 `relevant`·`faithful`·`reason`을 JSON으로 받는다 | LLM 1회 |

| 파일 | 변경 |
| --- | --- |
| `agent/validator.py` | `GroundedValidator`, `ungrounded_numbers`, 판정 프롬프트·스키마 |
| `agent/ollama_llm.py` · `openai_llm.py` · `fake_llm.py` | quality 클래스에 `judge()` — 백엔드마다 같은 인터페이스 |

## 한계와 트레이드오프

- **LLM 판정도 틀린다.** 실제 응답 원문 b1을 놓쳤다. 같은 유형의 합성 초안 b5는 잡았다 — 판정이 문장에
  따라 흔들린다. 다만 b1은 오분류에서 생긴 답이고, 항목 2 이후 그 질문은 장애로 분류되지 않는다.
  원인은 앞단(분류·대상 추정)에서 고치고 검수는 뒤를 받치는 구조다.
- **판정 이유의 분류가 부정확하다.** b6·b7(사실과 다른 결론)을 "질문과 관련 없는 답변"으로 분류했다.
  판정 결과는 맞지만 반려 사유를 재작성 지시로 쓰므로 이유가 엉뚱하면 재작성도 엉뚱해질 수 있다.
- **같은 계열 모델이 쓰고 판정한다.** 작성자와 판정자가 qwen3:8b라 같은 실수를 놓칠 수 있다.
- **장애 답변마다 LLM 호출이 하나 는다.** 검수 한 번에 약 3.5초. 반려되면 재작성까지 더해진다.
- **수치 대조가 엄격하다.** 수집값에서 계산한 값(예: "임계치보다 15%p 높음")도 수집 사실에 없는 수치로
  떨어진다. 정규식은 단위·버전 번호를 구분하지 않는다. 정상 초안 5건에서는 오탐이 없었다.
- **판정 JSON이 깨지면 통과로 둔다.** 판정기 고장으로 답변 자체를 막지 않으려는 선택이다.
- 3회째 실패를 경고와 함께 내보내는 것은 base의 "무한 재작성 방지"를 유지하기 위해서다. 질문 자체가
  잘못 분류된 경우에는 재작성으로 고칠 수 없어, 경고 붙은 답이 나간다.
