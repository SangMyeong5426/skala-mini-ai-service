# 0009: 과제 2 — 등급 점검 도메인을 새 패키지로 더하고, LLM 단독을 Before로 둔다

- 상태: Accepted
- 날짜: 2026-10-20
- 계획 항목: [`01-plan.md`](../01-plan.md) 공통 · 순번 7

## 문제

과제 1(Base 개선) 항목 1~5를 끝낸 뒤 과제 2(신규 주제)로 바꿨다. 주제는 게임 등급분류 사전 점검이다.
코드를 쓰기 전에 세 가지를 정해야 했다.

1. 인시던트 도메인 코드(`agent/graph.py`, `mcp_server.py`, 개선 항목 2~5)를 어떻게 할까.
2. 새 프로젝트라 "개선 전"이 없다. Before/After를 무엇과 무엇으로 비교할까.
3. 계획의 선택 항목 7(항목별 심사 서브에이전트)을 넣을까.

## 검토한 선택지

### A. 인시던트 코드를 등급 도메인으로 고쳐 쓴다

파일 수는 늘지 않는다. 대신 과제 1 테스트와 측정 도구가 전부 깨지고, 과제 1 결과를 다시 재현할 수 없다.

### B. 새 패키지 `agent/rating/`과 새 MCP 서버를 더하고 `AGENT_DOMAIN`으로 고른다

의존성 주입(`SupervisorDeps`), 의미 라우터, 검수의 수치 대조, MCP 클라이언트의 서버 조회, 스위치, 측정 도구를
그대로 쓴다. 기존 테스트도 그대로 돈다. 대신 서버 조립 코드(`server.py`)에 도메인 분기가 생긴다.

### C. Before = 과제 1의 Base 에이전트

주제가 달라 같은 입력으로 잴 수 없다.

### D. Before = 같은 모델의 LLM 단독

같은 모델(qwen3:8b)에 게임 설명만 주고 등급을 묻는다. 기준표·사례 검색·검수 없이. 에이전트의 부품마다
스위치를 두고 **모두 끈 상태가 곧 LLM 단독**이 되게 만들면, 같은 커밋·같은 평가셋에서 스위치만 바꿔 잴 수 있다.
부품을 하나씩 끄면 부품별 기여도 잴 수 있다.

### E. 항목 7 — 항목별 심사 서브에이전트

7개 내용정보 항목(폭력성·선정성·공포·언어·약물·범죄·사행성)마다 심사 에이전트를 두고 코드가 합친다.

## 결정

**B와 D를 택하고 E는 뺀다.**

- `AGENT_DOMAIN` 기본값은 `rating`이다. 기존 테스트는 `tests/conftest.py`에서 `incident`로 고정한다.
- 그래프 노드 이름과 이벤트 타입은 과제 1과 같게 둔다(route·plan·clarify·research·replan_check·analysis·write·validate·finalize).
  프론트(`web_chat.html`)를 고치지 않고 쓰고, "같은 뼈대에 도메인만 바꿨다"는 것을 코드로 보이기 위해서다.
- 등급 도메인은 MCP 서버로 `rating`(새로 만든 것)과 `docs`(원본의 decoy)를 띄운다. Tool·Resource를 어느 서버가
  제공하는지 미리 가정하지 않고 조회한 뒤 부르는 과제 1의 방식을 그대로 쓴다.

E를 뺀 이유:

1. **등급은 가장 높은 항목 하나로 정해진다.** 나머지 항목을 따로 심사해도 최종 등급에 더해지는 정보가 없다.
2. **과대평가가 늘어난다.** 최댓값 규칙에서는 어느 한 항목만 한 단계 높게 봐도 전체 등급이 오른다. 판정을 7번 따로
   하면 그중 하나라도 높게 볼 확률이 커진다.
3. **지연이 약 7배가 된다.** 로컬 ollama는 요청을 차례로 처리한다.
4. **잴 수 없다.** 정답 데이터(게임물관리위원회 API)에는 항목 이름만 있고 항목별 단계가 없다.

## 한계와 트레이드오프

- 두 도메인이 한 서버 코드에 있어 `server.py`의 조립 코드가 길어진다.
- LLM 단독은 "Base 에이전트"가 아니다. 같은 모델이 도구 없이 답할 때와 비교하는 것이다. 과제 요건이 말하는
  Before/After로 인정되는지는 확인 대기다([`followups.md`](../followups.md)).
- E를 빼서 Multi-Agent는 직접 다루지 않는다. 이 기록이 "검토했지만 쓰지 않은 이유"의 근거다.
