## 1. Agent Graph (LangGraph)

**무엇인가.** LangGraph 는 에이전트의 일하는 순서를 **순서도**로 짜는 라이브러리다. 순서도의 칸이 **노드**, 칸 사이 화살표가 **엣지**다.
화살표가 늘 같은 곳으로 가면 `add_edge`, 조건에 따라 갈라지면 `add_conditional_edges`(갈림길)를 쓴다.

**어떻게 도나.** 칸들은 **상태(State)** 라는 메모장 하나를 돌려 쓴다. 우리 것은 `RatingState` — 질문, 뽑은 장르·플랫폼, 찾은 사례, 판정 결과, 초안 등이 들어 있다.
노드는 메모장을 읽고, 바꿀 부분만 돌려준다. 그러면 LangGraph 가 메모장에 합쳐 넣고 다음 칸으로 넘긴다.

**갈림길은 이렇게 생겼다.**

```python
g.add_conditional_edges("route", _after_route, {"chat_answer": "chat_answer", "plan": "plan"})

def _after_route(state):
    return "chat_answer" if state["route"] == "chat" else "plan"
```

route 칸이 끝나면 `_after_route` 라는 판단 함수가 메모장을 보고 다음 칸 이름을 고른다. 우리 그래프에는 이런 갈림길이 다섯 곳 있다.

| 갈림길 | 조건 | Base / 새로 |
| --- | --- | --- |
| route | 제도 문의면 chat_answer, 아니면 plan | Base |
| plan | 설명이 부족하면 clarify, 아니면 research | 새로 |
| replan_check | 사례가 3건(`MIN_CASES`) 미만이면 범위를 넓혀 research 로 되돌아감 | Base(넓히는 규칙은 새로) |
| analysis | "무슨 게임인지 알 수 없다"면 clarify, 아니면 write | 새로 |
| validate | 불합격이면 write 로 되돌아감, 합격이면 finalize | Base |

**끝없이 돌지 않는 이유.** 되돌아가는 길이 두 개인데 둘 다 상한이 있다. 사례 범위는 장르+플랫폼 → 플랫폼 → 전체로만 넓혀서 최대 두 번,
재작성은 `MAX_ATTEMPTS = 3` 이다. 세 번째도 떨어지면 경고를 붙여 내보낸다.

**화면의 진행 표시.** 서버는 `graph.astream(...)` 으로 그래프를 돌리면서 노드가 끝날 때마다 그 노드가 남긴 기록을 브라우저로 바로 보낸다.
채팅 화면에 "비슷한 실제 결정 5건", "검수 통과" 같은 줄이 하나씩 뜨는 게 이것이다.

> **질문이 오면** — "LLM 에게 알아서 하라고 하지 않고 순서도를 짠 이유는?" → 순서와 갈림길을 코드로 정해 두면 LLM 이 단계를 건너뛰거나
> 끝없이 반복하지 못합니다. 또 칸마다 무엇을 했는지 기록이 남아 어디서 틀렸는지 찾을 수 있습니다.

## 2. 의존성 주입과 `partial`

**무엇인가.** 함수가 필요한 부품(사례 검색기, 검수기 등)을 **스스로 만들지 않고 밖에서 받는** 구조다.
비유하면 담당자에게 **공구 상자**를 쥐여 주는 것이다. 담당자는 상자에 든 공구를 쓰고, 공구가 없으면 기본 방식으로 일한다.

**우리 코드에서.**
- 공구 상자: [`SupervisorDeps`](../project/agent/deps.py#L15) — LLM, MCP 클라이언트, 그리고 부품 칸들(`router`, `case_retriever`, `assessor`, `clarifier`, `validator`, `law_answerer`).
- 상자 채우기: 서버가 켜질 때 [`server._build_rating_components`](../project/server.py#L197) 가 스위치 6개를 읽고, 켜진 부품만 만들어 넣는다.
- 상자 쥐여 주기: `g.add_node(name, partial(fn, deps=deps))`. `partial` 은 파이썬 기능으로, 함수에 넣을 값 하나를 **미리 채워 둔 새 함수**를 만든다.
  그래서 LangGraph 가 노드를 부를 때 메모장만 넘겨도 노드는 공구 상자까지 받는다.

**Before/After 가 여기서 나온다.** 노드는 부품이 비어 있으면(`None`) LLM 에게 그냥 묻는다. 예를 들어 analysis 는 판정기가 없으면
`quality_llm.rate_direct` 로 등급을 바로 묻는다. 그래서 스위치를 모두 끄면 같은 프로그램이 **LLM 단독(Before)** 이 된다.

**누가 만들었나.** `partial` 과 상자 자체는 Base, "부품이 비면 기본 동작" 규칙과 스위치는 과제 1, 등급분류 부품 5개
(사례 검색기 · 판정기 · 되묻기 · 검수기 · 법령 답변기)와 부품 칸 4개는 과제 2 에서 새로 만들었다.

> **질문이 오면** — "partial 이 뭐예요?" → 함수에 인자 하나를 미리 채워 둔 함수를 만드는 파이썬 기능입니다. 노드마다 부품 상자를 미리 채워 둡니다.
> "왜 이렇게 했어요?" → 부품을 빼거나 가짜로 바꾸기 쉬워서, 같은 프로그램으로 Before/After 를 재고 테스트도 진짜 AI 없이 돌립니다.

## 3. MCP — Tool · Resource

**무엇인가.** MCP(Model Context Protocol)는 에이전트가 외부 도구와 자료를 꺼내 쓰는 **표준 규격**이다.
자료를 내주는 쪽이 **서버**, 꺼내 쓰는 쪽(에이전트)이 **클라이언트**다. 비유하면 **표준 주문 창구** — 창구 모양이 정해져 있어서
어떤 서버든 같은 방법으로 주문할 수 있다. 우리 서버는 별도 프로그램으로 떠 있고, 에이전트와는 표준 입출력(stdio)으로 이야기한다.

**서버가 내주는 것 세 가지.**

| 종류 | 뜻 | 비유 | 우리 것 |
| --- | --- | --- | --- |
| Tool | 인자를 받아 실행하고 결과를 돌려주는 기능 | 계산해 주는 창구 | `rating_stats(genre, platform)` — 같은 장르·플랫폼의 등급 통계 |
| Resource | 주소(URI)로 꺼내 읽는 자료 | 서고의 책 | `criteria://descriptors`(기준표), `law://game-industry/rule-8`(시행규칙 제8조), `law://game-industry/articles`(법령 조문 148개), `ratings://cases`(실제 결정 1,751건) |
| Prompt | 서버가 정해 둔 지시문 | 업무 양식 | 우리 서버에는 없다. Base 인시던트 서버가 썼다 |

**코드로는.** 서버 쪽은 함수 위에 이름표 한 줄을 붙이면 된다.

```python
@mcp.tool()
def rating_stats(genre: str = "", platform: str = "") -> RatingStats: ...

@mcp.resource("criteria://descriptors")
def get_descriptor_criteria() -> str: ...
```

에이전트 쪽은 **먼저 찾고, 그다음 부른다.**

```python
server = await deps.mcp.find_tool("rating_stats")      # 이 도구가 있는 서버가 어디지? (과제 2 에서 추가)
data = await deps.mcp.call_tool("rating_stats", {"genre": g, "platform": p}, server=server)   # Base
```

[`find_tool`](../project/agent/mcp_client.py#L91) 은 연결된 서버들에 차례로 "도구 목록"을 물어 그 이름이 있는 서버를 돌려준다.
자료(Resource)도 같은 식으로 `find_resource` → `read_resource` 한다.

**왜 찾아서 쓰나.** 서버 이름을 코드에 박아 두면 자료를 다른 서버로 옮길 때 에이전트를 고쳐야 한다. 찾아서 쓰면 에이전트 코드는 그대로다.
Base 가 처음부터 이 원칙으로 짜여 있었다(Base 는 Resource 템플릿과 Prompt 를 찾아 썼다).

> **질문이 오면** — "Tool 과 Resource 차이는?" → Tool 은 인자를 받아 계산해 주는 기능이고, Resource 는 주소로 읽기만 하는 자료입니다.
> "그냥 파이썬 함수로 부르면 되지 왜 MCP 로?" → 자료를 내주는 쪽을 별도 서버로 떼어 표준 방식으로 부르면, 자료를 바꾸거나 다른 에이전트가 같은 서버를 쓸 때 에이전트 코드를 고치지 않아도 됩니다.

## 4. RAG — 임베딩 · 코사인 유사도

**무엇인가.** RAG(Retrieval-Augmented Generation, 검색 증강 생성)는 LLM 이 답하기 전에 **관련 자료를 먼저 찾아(Retrieval)**
프롬프트에 붙여 주고(Augmented), **그 자료를 보고 답하게(Generation)** 하는 방식이다. 비유하면 **오픈북 시험**이다.

**찾는 방법 — 임베딩과 코사인 유사도.**
1. **임베딩**: 문장을 숫자 묶음(벡터)으로 바꾼다. 뜻이 비슷한 문장은 비슷한 숫자 묶음이 된다. 우리는 로컬 모델 `qwen3-embedding:0.6b` 를 쓴다.
2. **코사인 유사도**: 두 숫자 묶음을 화살표로 보고 방향이 얼마나 같은지 잰다. 1 에 가까울수록 뜻이 비슷하다.
3. **상위 k 개**: 모든 자료와 유사도를 재서 높은 순으로 k 개만 고른다.

```python
[query_vec] = await self.embedder.embed([text])                                   # 1. 설명을 숫자로
ranked = sorted(((cosine(query_vec, self.vectors[i]), i) for i in candidates),
                reverse=True)[:self.k]                                             # 2·3. 가까운 순으로 5개
```

자료 쪽 숫자 묶음은 서버가 켜질 때 한 번 만들어 파일로 저장해 둔다(`data/ratings/.embed-cache/`). 그래서 두 번째부터는 빨리 뜬다.

**우리 RAG 세 곳.**

| 어디 | 찾는 것 | 찾은 뒤 | 코드 |
| --- | --- | --- | --- |
| 사례 검색 | 실제 결정 1,751건 중 가장 비슷한 5건 | 3건 미만이면 범위를 넓혀 다시. 판정 LLM 이 이 사례들을 보고 항목 수위를 판단 | [`cases.py`](../project/agent/rating/cases.py#L105) |
| 법령 답변 | 조문 148개 중 질문과 가까운 4개 | 그 4개만 보고 답하게 하고, 인용 조문·숫자를 코드가 검사. 어기면 "답할 수 없습니다" | [`law.py`](../project/agent/rating/law.py#L77) |
| 질문 분류 | 예시 문장 30개(대화 15, 점검 15) | 어느 쪽 예시와 더 가까운지로 분류. 차이가 0.04 미만이면 작은 LLM 에 넘김 | [`router.py`](../project/agent/router.py#L57) (과제 1 코드) |

**왜 RAG 인가.** LLM 혼자 답하면 "청소년이용불가는 14세 이상"처럼 지어낸다. 찾은 자료만 보고 답하게 하고 인용을 검사하면,
근거를 함께 보여 줄 수 있고 근거가 없을 때는 답하지 않게 할 수 있다.

**Base 에는?** Base 도 자료를 찾아 와서 답에 붙이는 구조는 있었다. 다만 **이름으로 정확히 꺼내는** 방식이었다 — 시스템 이름으로 모니터링 상태(MCP Tool),
장애 유형으로 runbook 파일(MCP Resource)을 꺼내고, 어느 runbook 을 꺼낼지는 알림 문구의 **키워드 규칙**("timeout" → network-timeout)으로 골랐다.
뜻이 비슷한 것을 찾는 임베딩 검색은 없었다. 키워드 규칙을 임베딩으로 바꾼 것이 과제 1이고, 그때 만든 임베딩 클라이언트와 `cosine` 을 과제 2 의 사례·법령 검색에 다시 썼다.

**한계도 같은 곳에서 나온다.** 찾은 자료가 엉뚱하면 답도 엉뚱해진다. 개요가 없는 사례가 제목·장르만 비슷해 "가장 비슷한 사례"로 뽑힌 일이 그 예다(보고서 4절).

> **질문이 오면** — "임베딩이 뭐예요?" → 문장을 숫자 묶음으로 바꿔 뜻이 얼마나 비슷한지 계산할 수 있게 하는 것입니다.
> "코사인 유사도는?" → 두 숫자 묶음이 가리키는 방향이 얼마나 같은지 재는 값이고, 1 에 가까울수록 비슷합니다.

## 5. 판정은 LLM 과 코드가 나눠 한다

**LLM 이 하는 일.** 7개 항목(폭력성·선정성·공포·언어·약물·범죄·사행성)마다 해당 여부, 단계(0~3), 그렇게 본 근거 구절을 낸다.

**코드가 하는 일** ([`assess.py`](../project/agent/rating/assess.py#L33)).
1. `quote_found` — 근거 구절이 정말 게임 설명에 있는지 확인하고, 없으면 그 항목을 지운다(LLM 이 지어낸 근거를 걸러냄).
2. `rating_from_items` — 남은 항목 중 **가장 높은 단계**가 등급이다(단계 0·1·2·3 = 전체·12세·15세·청소년이용불가).
3. `combine` — 가장 비슷한 실제 사례의 등급을 하한으로 쓴다(R1, 낮게 보는 실수를 줄이려고).

> **질문이 오면** — "왜 LLM 에게 등급을 바로 안 물어요?" → 바로 물었더니 등급과 근거가 어긋났습니다. 계산을 코드로 옮기면 보고서의 등급과 근거가 늘 맞습니다.

## 6. 검수와 LLM-as-judge

**LLM-as-judge** 는 LLM 에게 채점을 시키는 방법이다. 다만 채점관도 틀릴 수 있어서, 답이 정해진 검사는 코드가 먼저 한다
([`check.py`](../project/agent/rating/check.py#L93)).

| 순서 | 누가 | 보는 것 |
| --- | --- | --- |
| 1 형식 | 코드 | "예상 등급:" 줄이 있는가 |
| 2 등급 | 코드 | 보고서의 등급 = 코드가 계산한 등급 |
| 3 사례 | 코드 | 인용한 사례가 실제로 찾아온 사례이고 등급이 맞는가 |
| 4 숫자 | 코드 | 보고서의 숫자가 통계·사례·설명에 있는가 |
| 5 뜻 | LLM | 질문한 그 게임 이야기인가, 판정과 맞는가 |

앞에서 떨어지면 LLM 채점을 부르지 않는다(싸고 정확한 것부터). 떨어진 이유는 재작성 지시로 write 에 돌려준다.

## 7. Multi-Agent 와 뺀 이유

**무엇인가.** 여러 에이전트가 역할을 나눠 일하는 구조다. 예를 들어 "폭력성 심사 에이전트", "선정성 심사 에이전트"를 따로 두는 식이다.

**왜 뺐나** ([결정 0009](decisions/0009-rating-domain.md)).
- 등급은 가장 높은 항목 **하나**로 정해져서, 항목별로 나눠 심사해도 정보가 늘지 않는다.
- 판정을 7번 따로 하면 그중 하나라도 높게 볼 확률이 커져 과대평가가 늘고, 로컬 모델은 요청을 하나씩 처리해 지연이 약 7배가 된다(추정).
- 정답 데이터에 항목별 단계가 없어 효과를 잴 수도 없다.

## 8. LangSmith

노드와 LLM 호출마다 무엇이 들어가고 나왔는지 기록해 웹 화면으로 보여 주는 도구다. 함수 위에 `@traceable` 을 붙이면 기록된다
(등급 모듈에 30곳). 에이전트가 어디서 틀렸는지 찾을 때 쓴다. `.env` 에 LangSmith 설정(`LANGCHAIN_TRACING_V2`, API 키)이 있을 때 기록된다.

## 9. 질문이 오면 — 한 줄 답 모음

| 질문 | 답 |
| --- | --- |
| Agent Graph 를 쓴 이유는? | 순서와 갈림길을 코드로 정해 LLM 이 단계를 건너뛰거나 끝없이 돌지 못하게 했습니다 |
| 갈림길은 어떻게 만드나요? | `add_conditional_edges` 에 판단 함수를 넘깁니다. 판단 함수가 메모장을 보고 다음 노드 이름을 고릅니다 |
| partial 이 뭐예요? | 함수에 인자 하나를 미리 채워 둔 함수를 만드는 파이썬 기능입니다. 노드마다 부품 상자를 미리 채워 둡니다 |
| 의존성 주입을 왜? | 부품을 빼면 LLM 단독이 되어 같은 프로그램으로 Before/After 를 재고, 가짜 부품으로 테스트합니다 |
| Tool 과 Resource 차이는? | Tool 은 인자를 받아 계산해 주는 기능, Resource 는 주소로 읽기만 하는 자료입니다 |
| 왜 MCP 로? | 자료를 별도 서버로 떼어 표준 방식으로 부르면, 자료를 바꿔도 에이전트 코드를 고치지 않습니다 |
| find_tool 은 왜 추가했나요? | Base 에는 Tool 이 있는 서버를 찾는 기능이 없었습니다. 등급 통계 Tool 을 서버 이름 없이 부르려고 넣었습니다 |
| RAG 가 뭐예요? | 답하기 전에 관련 자료를 찾아 그것만 보고 답하게 하는 방식입니다 |
| 왜 코사인 유사도인가요? 다른 거리와 비교해 봤나요? | 임베딩 검색의 기본 방식이라 썼습니다. 저장된 벡터 3,295개(사례 1,751·1,396, 조문 148)의 길이가 모두 1(정규화)이라 코사인·내적·유클리드 거리는 가까운 순서가 똑같습니다 — 바꿔도 고르는 결과는 같습니다(2026-10-21 캐시로 확인). 찾는 방식 자체를 키워드 검색(BM25)으로 바꿔 개발용 38문항에서 비교해 보니 임베딩이 같거나 나았습니다(5건 다수결 23 vs 22, 1건 20 vs 16) |
| Base 에도 검색이 있지 않았나요? | Base 도 이름과 키워드로 매뉴얼을 꺼내 와서 답에 붙이는 구조는 있었습니다. 뜻이 비슷한 사례를 찾는 임베딩 검색은 없었고, 그건 과제 1에서 넣고 과제 2에서 사례·법령 검색으로 넓혔습니다 |
| 임베딩 · 코사인 유사도는? | 문장을 숫자 묶음으로 바꾸고, 두 묶음의 방향이 얼마나 같은지로 비슷한 정도를 잽니다 |
| 왜 5건, 4개인가요? | 설계할 때 정한 값입니다. 조문은 더 넣으면 프롬프트가 길어지고 줄이면 답이 든 조문을 놓칠 수 있어 4개로 뒀습니다([결정 0015](decisions/0015-law-grounded-answers.md)). 사례는 3건 미만이면 범위를 넓힙니다 |
| LLM 이 틀리면? | 등급 계산·근거 확인·숫자 대조는 코드가 하고, 뜻만 LLM 이 봅니다. 그래도 놓친 경우(법령 1건)는 한계로 밝혔습니다 |
| Multi-Agent 는? | 등급이 가장 높은 항목 하나로 정해져 나눠 심사해도 이득이 없고, 과대평가와 지연만 커져 뺐습니다 |
