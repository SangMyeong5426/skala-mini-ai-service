## 2. 개선 포인트

| 항목 | 무엇을 | 어떻게 | 기술 요소 |
| --- | --- | --- | --- |
| 1 | thinking 출력 제어 | 분류·계획·작성·검수는 생각을 끄고(`OLLAMA_THINK`), 대화만 켠다(`OLLAMA_THINK_CHAT`). LLM 생성자에 주입 | 의존성 주입, 설정 분리 |
| 2 | 의미 라우터 | 예시 문장 40개를 임베딩해 두고 질문과의 유사도(상위 3개 평균)로 chat/incident 판정. 두 점수 차가 0.029 미만일 때만 LLM에 넘김 | RAG(임베딩 검색), 모듈화 |
| 3 | 대상 시스템 추정 + 되묻기 | 시스템 카탈로그를 **MCP Resource**(`catalog://systems`)로 제공. 이름 매칭 → 대상 밖 이름 판별 → 설명 임베딩 → 못 정하면 **새 `clarify` 노드**가 진단 대신 되묻는다(LLM 없음) | MCP, RAG, 그래프 개선 |
| 4 | 검수 근거 검증 | 형식 → **수치 대조**(초안 수치가 수집값에 있는지, 코드) → **LLM-as-judge**(질문 관련성·사실 일치, JSON) 순서. 싼 검사에서 떨어지면 LLM을 부르지 않음 | 평가(LLM-as-judge) |
| 5 (선택) | runbook 의미 검색 | runbook 6종을 임베딩(메타데이터 = incident_type)해 "질문 + 알림 문구"로 검색 | RAG |
| 공통 | 구조·검증 | 새 모듈 5개를 `SupervisorDeps`로 주입, **개선마다 환경변수 스위치 6개**(끄면 원본 동작 그대로 → 같은 서버로 전/후 재현), 새 단계 모두 LangSmith `@traceable`, 단위 테스트 **6 → 66개** | 의존성 주입, 모듈화, LangSmith, 단위 테스트 |

**판정 기준은 평가 세트로 고르지 않았다.** 라우터 margin은 예시 문장 안의 leave-one-out으로, 대상 추정의 임계값은
평가 세트와 별개인 조정용 문장 18개로 정했다. 평가 세트로 고르면 정답을 외운 것이 되기 때문이다.

### 3-3. 개선 하나만 적용했을 때 — 속도와 판단의 맞바꿈

thinking만 끈 상태(항목 1만 적용, 1회 측정)에서는 회귀 쿼리 합계가 411초 → 101초로 빨라졌지만, 0.6b의 판단이
거칠어져 대상 정확도가 6/15 → **5/15**, 엉뚱한 진단이 7 → **10건**으로 나빠졌고 "제 이름은 민수입니다"를 장애로
분류했다. 항목 2·3이 판단을 임베딩과 코드로 옮기면서 이 손실을 메웠다. 개선 항목은 함께 써야 의미가 있다.

## 부록 — 측정 방법과 근거 파일

- **같은 입력**: 회귀 쿼리 10개(11턴), 라벨 평가 세트 4종(분류 30 · 대상 15 · 검수 12 · runbook 10).
- **같은 코드 기준**: 원본 첫 커밋에 `base` 태그. `scripts/measure-at`이 잴 커밋을 git worktree로 따로 꺼내 그 코드로 잰다.
- **질문끼리 간섭 없음**: 회귀 쿼리는 질문마다 서버를 새로 띄운다. base는 timeout 뒤에도 서버가 생성을 계속해 다음 질문을 막기 때문이다.
- **편차 처리**: 1회 측정 편차가 ±30% 안팎이라 사용자 체감 수치는 반복 3회 중앙값으로 확정했다.
- `cost_usd`는 토큰 수 × 가상 단가 추정이다(로컬 추론이라 실제 청구는 없다).
