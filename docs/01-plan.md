## 측정 계획

**Before = LLM 단독, After = 에이전트.** 새 프로젝트라 "개선 전"이 없으므로, 같은 모델에 게임 설명만
주고 등급을 묻는 것(도구·기준·검수 없음)을 Before로 둔다. 스위치를 모두 끈 상태가 Before다.

| 지표 묶음 | 입력 | 비교 |
| --- | --- | --- |
| 등급 정확도 (실데이터) | 평가셋 A — 2026-07~09 결정분에서 등급별 10개씩 40개. 입력은 개요·장르·플랫폼, 내용정보는 정답 쪽에만 둔다 | 정확도, ±1단계 정확도, **과소평가 건수**(실제보다 낮게 본 것 — 가장 위험한 오류), 내용정보 F1 |
| 기준 적용 (상세 설명) | 평가셋 B — 직접 쓴 상세 설명 20개, 요약표로 매긴 라벨 (시간이 남으면) | 등급·항목 단계 정확도 |
| 검수 탐지율 | 평가셋 C — 정상 5 + 오염 7(없는 조항, 사례 등급 조작, 단계·등급 불일치) | 탐지율·오탐률 |
| 지연·비용 | 회귀 쿼리 10개 | `measure_queries.py`·`scripts/measure-at` 그대로 |

- 백엔드는 ollama로 고정한다. 과제 1과 같은 모델을 쓴다.
- 평가셋 A는 개요가 짧아(중앙값 43자) 절대 정확도가 낮게 나올 것이다. 전/후 비교로만 쓴다.
- 라벨은 개선 코드를 보고 고치지 않는다. 평가셋 B는 라벨과 에이전트가 같은 요약표에 기대므로 순환이 있다 — 한계로 적는다.

## 미리 보이는 한계

- 실데이터 개요가 한 문장이라, 등급을 가른 요소(예: 선정성)가 개요에 안 보이는 경우가 많다.
- 정답에 잡음이 있다. 같은 수위인데 등급이 다르다는 업계 비판이 있다.
- 요약표의 "단계 = 등급" 대응은 요약일 뿐이고, 실제 판단은 위원회가 주제와 맥락까지 보고 내린다.
- 결과는 법적 판단이 아니라 참고용이다.
- 캐시한 시점 이후의 결정은 반영되지 않는다.

## 확인하지 못한 것

- 사례집 페이지 문구를 저장소에 옮겨도 되는지(홈페이지 저작권 정책)
